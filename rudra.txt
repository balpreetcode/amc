================================================================================
ROOT CAUSE ANALYSIS: Video Generation Permission Issue
================================================================================

ISSUE SUMMARY:
--------------
Video generated at 1/7/2026, 10:56:51 AM is accessible via play button
Video generated at 1/7/2026, 12:06:59 PM gives error: "Failed to load video.
The file may have been generated in a different environment (Docker)."
Permission fixes work temporarily but break again after some time.

ROOT CAUSE:
-----------
FOUR backend servers running simultaneously, all competing for the same
Conductor tasks and writing files to different locations with different owners.

RUNNING BACKENDS:
-----------------
usr2      82893  node server.js  (current, started 08:03 today, listening on port 3002)
root    1948418  node server.js  (started Jan 06, running for 2 days)
ubuntu  2031686  node server.js  (started Jan 06, running for 2 days)
Docker: workflow-backend container (running for 20 hours)
Docker: workflow-frontend container (running for 21 hours)

WHAT'S HAPPENING STEP BY STEP:
-------------------------------
1. You click "Run" in the frontend
2. Frontend sends request to backend
3. MULTIPLE backends are ALL polling Conductor for tasks
4. ANY backend can pick up the task - it's unpredictable which one
5. The chosen backend generates the video and writes to its own output directory:

   Docker backend       → /app/output (inside container, mounted to Docker volume)
   Root backend         → /home/usr2/code/output (owned by root:root)
   Ubuntu backend       → /home/usr2/code/output (owned by ubuntu:ubuntu)
   Usr2 backend (current) → /home/usr2/code/output (owned by usr2:ubuntu)

6. Frontend tries to play video via /output/composed_XXX.mp4
7. Video not found or access denied because:
   - If Docker generated it: File is in Docker volume, not accessible by local backend
   - If root/ubuntu generated it: File permissions prevent usr2 backend from serving it

OUTPUT DIRECTORY STATE:
-----------------------
Location: /home/usr2/code/output
Permissions: drwxrwsr-x  usr2 ubuntu
- Setgid bit means new files inherit the ubuntu group
- But file owner depends on which process created it

FILES IN OUTPUT DIRECTORY:
--------------------------
-rwxrwxr-x  usr2 ubuntu  (files with full permissions - created when usr2 had group access)
-rw-r--r--  usr2 ubuntu  (read-only for group - created after permission changes)

WHY PERMISSIONS KEEP BREAKING:
-------------------------------
When you "fix permissions" via chmod/chown:
1. Fix works for existing files
2. But then ROOT backend creates new files → Owned by root:root → Breaks again
3. Or UBUNTU backend creates new files → Owned by ubuntu:ubuntu → Breaks again
4. Or DOCKER backend creates files → In container volume, not on host filesystem

Each backend creates files with its own user ownership, so fixes are temporary.

WHY VIDEO AT 10:56 AM WORKS:
-----------------------------
The video file at 10:56 AM was likely created by usr2 backend when it was the
only one running properly. Files owned by usr2:ubuntu are accessible by the
current usr2 backend server running on port 3002.

WHY VIDEO AT 12:06 PM FAILS:
----------------------------
The video was likely generated by one of the OTHER backends:
1. Docker backend → File in Docker volume, NOT in /home/usr2/code/output
2. Root backend → File owned by root, causing permission issues
3. Ubuntu backend → File owned by ubuntu, causing permission issues

WHY THE ERROR MESSAGE SAYS "DIFFERENT ENVIRONMENT (DOCKER)":
------------------------------------------------------------
The frontend error handler catches video loading failures and shows a generic
error message. This doesn't necessarily mean Docker - it could be any permission
or file-not-found issue. The actual cause is the multi-backend conflict.

MULTI-BACKEND CHAOS:
--------------------
All four backends are:
- Polling Conductor for tasks simultaneously
- Competing for the same workflow executions
- Writing files to different locations with different permissions
- Making it unpredictable which backend will handle any given workflow

SOLUTION:
---------
1. Kill ALL conflicting backend processes:
   sudo kill 1948418  # Kill root backend
   sudo kill 2031686  # Kill ubuntu backend
   sudo docker stop workflow-backend  # Stop Docker backend
   sudo docker stop workflow-frontend  # Stop Docker frontend

2. Run ONLY ONE backend - either Docker OR local, NOT both:

   Option A - Docker only:
   - docker compose up -d
   - Don't run 'node server.js' locally

   Option B - Local only:
   - cd backend && node server.js
   - Keep Docker containers stopped

3. Verify only ONE backend is running:
   ps aux | grep "node server.js" | grep -v grep
   # Should show only ONE process

4. Ensure consistent OUTPUT_DIR:
   - Local backend uses: /home/usr2/code/output
   - Docker backend uses: /app/output (mapped to volume)

ADDITIONAL NOTES:
-----------------
- The .env file has no OUTPUT_DIR set, so it defaults to relative path
- Frontend connects to backend via BACKEND_URL or proxy
- When multiple backends run, they create unpredictable file ownership
- Permission fixes are temporary because they don't stop the root cause
